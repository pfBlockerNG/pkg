pfBlockerNG

Self-hosted FreeBSD pkg repository for pfSense CE & pfSense Plus.

Install pfBlockerNG straight from this repository: pick a channel below and run its commands on your firewall (as root). Every channel installs the same canonical package (pfSense-pkg-pfBlockerNG) from its own repository — see Trust & channel model below for how the four relate.

Channels

Stable

not yet published

Final tagged releases (X.Y.Z) from a maintained release line. Production use.

fetch -qo - https://pfblockerng.github.io/pkg/add-repo.sh \
  | sh -s -- --base-url https://pfblockerng.github.io/pkg --channel stable
pkg install pfSense-pkg-pfBlockerNG
Manual conf (advanced)

The bootstrap auto-detects this; in a hand-written conf, replace <varver> (the edition-version: ce-2.8, plus-26.03, …) with your box's value.

# Generated at boot by pfblockerng_repo_generate (ADR-39) — do not edit; re-run add-repo.sh to change.
# pfBlockerNG (stable channel) — self-hosted pkg repository (ADR-17).
# NONE-signed: trust anchor is HTTPS to the host (no signing key). The URL is
# fully resolved for this box's edition/version (ADR-39; arch-less/NO_ARCH,
# issue #1806); the boot rc.d hook updates it on a pfSense OS upgrade.
# priority 100 sits above the base Netgate `pfSense` repo so cross-repo
# resolution (pkg install/upgrade, GUI Install) selects the pfBlockerNG build.
pfblockerng-stable: {
  url: "https://pfblockerng.github.io/pkg/stable/<varver>",
  mirror_type: none,
  signature_type: none,
  priority: 100,
  enabled: yes
}

Trust & channel model

One tagged artifact, several catalogues

Stable, Testing, and Edge may intentionally serve the exact same canonical package — same name, same version, same bytes — because a single tagged release always fans out to every channel its tag kind reaches: a Stable final lands in Stable, Testing, and Edge; a Testing prerelease lands in Testing and Edge; an Edge patch-zero prerelease lands in Edge alone. Edge's own latest simply moves ahead numerically once a new release family opens there — the fan-out itself never depends on what else has been published. This is catalogue placement, not separate builds, and not a repository-priority policy.

Trust model

Every repository conf sets signature_type: none — there is no catalogue-signing key. The trust anchor is HTTPS/TLS to this Pages host.

Single-repository subscription

A box subscribes to exactly one channel repository at a time. The four channel repos share one equal priority (100), above the base Netgate pfSense repo (priority 0); live pkg resolution at equal priority ignores version ordering between repos, and upgrades of an installed package never leave its origin repository — so enabling a second project channel repo is not how channel selection works. This is safe because each channel catalogue strictly contains everything its slower channels carry: Edge holds every package Testing does, and Testing holds every package Stable does, so a Stable final always lands in Stable, Testing, and Edge; a Testing prerelease always lands in Testing and Edge; an Edge patch-zero prerelease lands in Edge alone. One subscription therefore already has every package a box could need, because pkg orders versions numerically, component-wise — never by release date: if Edge holds 4.0.0.a2 and a later 3.2.16.a3 or 3.2.17 is published into it, the latest in Edge stays 4.0.0.a2, and the older build stays in the Edge catalogue as in-repo rollback material. Switching forward (to a higher version) is replacing the enabled conf with the faster channel's and upgrading normally. Rolling back is an explicit repository-qualified downgrade/reinstall — available within the same repo on a faster channel (containment keeps the older build around), or after switching the conf to a slower channel. Removing a channel means removing its conf. Identical name/version across catalogues remains valid only because the bytes and provenance are identical.

Retention

Each <channel>/<varver>/ catalogue retains the newest 5 canonical packages; a faster channel additionally retains any canonical package one of its slower channels still retains, so containment (Edge ⊇ Testing ⊇ Stable) survives retention, not only fan-out. Dependency packages are not pruned.

Netgate identity

The canonical package shares its name with the pfBlockerNG package Netgate ships in its own pfSense repo — provenance differs. Every build published here carries commit/created annotations linking it to the source commit that produced it; repository priority decides which build pkg selects when both are enabled.

Channel switching

Switching channels is two steps, and the second one is not optional. https://pfblockerng.github.io/pkg/add-repo.sh run with --channel <ch> moves the subscription: it writes that channel's conf and retires every other project conf. It does not move the installed package — pkg keeps an installed package pinned to its origin repository and offers no upgrade across repositories, so a box that only gains a conf silently keeps running its old build. https://pfblockerng.github.io/pkg/migrate-channel.sh run with the same --channel <ch> performs the repository-qualified operation that actually moves it, replaces a legacy suffixed identity (-devel, -nightly) with the canonical package, and verifies the result before reporting success. There is no in-UI channel switcher by design.

fetch -qo - https://pfblockerng.github.io/pkg/add-repo.sh \
  | sh -s -- --base-url https://pfblockerng.github.io/pkg --channel <ch>
fetch -qo - https://pfblockerng.github.io/pkg/migrate-channel.sh \
  | sh -s -- --channel <ch>
